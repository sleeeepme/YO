# YO

「今飲みたい・雑談したい」を友達に伝え、SNS から気軽にボイスチャットへ参加できるサービス。

YO はリアルな友達を中心に、友達の友達まで同じテーブルで話せる体験を目指します。
Modern / Pop な、親しみやすいキャラクター中心の UI を採用します。

## ユーザー体験 — Value → Signup

1. サービスの価値や招待されたテーブルの雰囲気を、登録前に見る。
2. 「参加する」「テーブルを作る」など、必要な時点で登録・ログインする。
3. 初回はランダムアバターを自動生成し、すぐに使い始められる。
4. 認証後は元の招待・操作へ戻り、入室条件を確認してボイスチャットに参加する。

アバター作成は必須にしません。後から **Shuffle / Customize** ができる設計にします。
登録前のプレビューには公開可能な情報だけを表示し、通話への参加には認証と認可を必要とします。

## SNS 連携 — Instagram / X / Discord / LINE

SNS は主に **ログイン・本人識別・招待経路** として使います。

| 対象 | 連携の目標 |
| --- | --- |
| Instagram | 招待リンク・カードの共有、利用可能な本人識別・アカウント連携 |
| X | 招待リンク・OGP の共有、利用可能なログイン・アカウント連携 |
| Discord | 招待リンクの共有、利用可能なログイン・アカウント連携 |
| LINE | 招待リンクの共有、利用可能なログイン・アカウント連携 |

これは対象と目的の整理であり、各 API の対応可否を保証する表ではありません。SNS ごとに公式仕様・権限・審査を確認して実装します。
すべての SNS の OAuth、友達一覧の取得、自動投稿が同じように利用できるとは想定しません。
共有はリンクコピーを基礎にし、ログイン連携とは独立して実装します。YO の友達関係を、SNS のフォロー関係や申告されたアカウント名だけで判定しません。

## ボイスルーム

| 項目 | 仕様 |
| --- | --- |
| 既定の定員 | 8 人 |
| 最大人数 | 8 人 |
| ホストが設定できる定員 | 2〜8 人 |
| 満員表示 | 8 人定員なら 8/8 = FULL。設定定員に達したら満員 |
| 満員時の導線 | 「別テーブルを作る」 |
| 既定の入室権限 | Friends + Friends |

定員はホストを含む人数として設計します。

**Friends + Friends** の入室ルール：

- 友達：自動入室。
- 友達の友達：自動入室。
- その他：承認が必要。

リンクを持っているだけでは自由入室できません。自動入室や承認済みのユーザーも、満員・終了・期限切れの場合は参加できません。
関係判定の基準人物と承認者の詳細は要決定です。ブロック関係は自動入室より優先する方針です。

## 招待カード・OGP

招待カードに表示可能な情報：

- ルーム名。
- 現在の参加人数 / 最大人数、残りの席数。
- メンバーアイコン・メンバー名。
- 残り時間。

表示例：

> FRIDAY DRINK  
> Kenta / Yuki / +2  
> 6 / 8  
> あと2人

共有 URL には招待ランディングと OGP を用意します。メンバー情報は公開範囲と本人の同意に応じて省略できるようにします。
OGP は SNS 側でキャッシュされ、第三者にも見られるため公開可能な情報だけを使います。人数・残り時間は取得時点の情報で、実際の入室可否はサーバーで再確認します。
ルームの制限時間や招待の具体的な有効期限は未確定です。

## 技術構成

| 技術 | 役割 |
| --- | --- |
| Next.js + TypeScript | Web UI、招待ページ、OGP、サーバー API |
| Supabase | 認証、プロフィール、友達関係、ルーム・参加・承認・招待のデータ |
| LiveKit | リアルタイム音声、ミュート、接続・切断・再接続 |
| Vercel | GitHub と連携したプレビュー・本番配信の想定先 |

LiveKit トークンは Next.js のサーバー側で、Supabase に基づく認証・認可と定員確認を終えてから発行します。
参加枠は原子的に確保し、同時入室、接続失敗、離脱、再接続で人数制限が崩れないようにします。
Supabase のデータ変更はマイグレーションで管理します。スキーマやパッケージバージョンは実装時に選定します。

## MVP の優先順位

以下は推奨する実装順序です。セキュリティは各段階で組み込みます。

1. Next.js の最小起動版、価値の説明、登録前の招待プレビュー。
2. Supabase 認証、プロフィール、ランダムアバター。
3. 友達関係、ルーム作成、Friends + Friends、承認、2〜8 人の定員制御。
4. LiveKit による入退室・音声・ミュート・再接続、満員時の別テーブル作成。
5. 招待リンク・カード・OGP と SNS への共有。
6. 認可・RLS・同時入室・公開範囲を検証し、α版を配信。

追加 SNS の認証連携、詳細なアバターカスタマイズ、高度な通知は後続候補です。
課金・録音・文字起こし・映像通話・SNS 自動投稿は MVP の確定要件に含めません。

## セキュリティ方針

- Supabase の公開スキーマのテーブルに RLS と最小権限を設定する。
- サーバーで本人・関係・承認・定員・期限を検証し、クライアントの申告を信頼しない。
- LiveKit トークンは対象ルーム・ユーザー・最小権限・短い有効期限に限定する。
- 定員確認と参加枠確保を原子的に行い、予約の期限切れと再接続も処理する。
- 招待を推測しにくくし、期限・失効・レート制限を設ける。
- OAuth の安全要件、Cookie 認証での CSRF 対策、入力検証を実装する。
- ブロック・承認・退出管理を認可に反映する。
- 公開カード／OGP に非公開メンバー情報や秘密値を載せない。
- 秘密値や認証トークンを Git・ログ・ブラウザーへ出さない。
- マイクの許可拒否と通信エラーを扱う。音声を無断で録音・保存しない。

詳細な実装上の注意と検証条件は [AGENTS.md](AGENTS.md) を参照してください。

## 実行方法

### 今できること

リポジトリを取得し、仕様を確認できます。

```bash
git clone https://github.com/sleeeepme/YO.git
cd YO
```

**現時点では package.json がないため、npm install / npm run dev でアプリを起動できません。**
まず AGENTS.md に沿って Next.js の最小版を実装する必要があります。

### Next.js 実装後の想定手順

以下は npm を採用し、package.json の dev / build / start スクリプトと .env.example を追加した後に使う手順です。実装時に実際の構成へ更新してください。

1. package.json に指定した Node.js / パッケージマネージャーを準備する。
2. 依存関係をインストールする。package-lock.json がある場合は npm ci、まだない場合は npm install を使う。
3. 実装に合わせた .env.example を .env.local にコピーし、ローカル用の値を設定する。
4. Supabase の開発用プロジェクトまたはローカル環境を用意し、実装されたマイグレーションを適用する。
5. LiveKit の開発用接続先とサーバー資格情報を用意する。認証方式に応じて開発用コールバック URL も設定する。
6. 開発サーバーを起動する。

```bash
npm ci
cp .env.example .env.local
npm run dev
```

通常の確認先は http://localhost:3000 です。ポートが変更された場合は起動時の表示に従います。
実際の音声確認はマイクが利用できる localhost または HTTPS で、複数ユーザー／端末を使って行います。

ビルド・本番モードの想定コマンド：

```bash
npm run build
npm run start
```

型検査・lint・テスト・DB セットアップのコマンドは、追加されたスクリプトとマイグレーションに合わせて文書化します。未設定の外部サービスを、動作済みとして扱いません。

## 環境変数方針

以下は実装時の**推奨変数名**です。まだコードや .env.example との対応はありません。値は記載しません。

| 変数名 | 用途 | 公開可否 |
| --- | --- | --- |
| NEXT_PUBLIC_APP_URL | 招待・OGP・認証後の戻り先に使うアプリ URL | 公開可 |
| NEXT_PUBLIC_SUPABASE_URL | Supabase の接続 URL | 公開可 |
| NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY | Supabase の公開用キー。RLS と併用 | 公開可 |
| SUPABASE_SERVICE_ROLE_KEY | 必要なサーバー管理操作だけに使用 | サーバー専用・秘密 |
| LIVEKIT_URL | サーバーが使用する LiveKit 接続先。クライアントへ渡す場合も秘密として扱わない | 公開可能な接続先 |
| LIVEKIT_API_KEY | LiveKit トークン署名に使う資格情報 | サーバー専用 |
| LIVEKIT_API_SECRET | LiveKit トークン署名の秘密値 | サーバー専用・秘密 |

実装・既存プロジェクトが公開用の anon key を使う構成の場合は NEXT_PUBLIC_SUPABASE_ANON_KEY に揃えます。公開用キー名を混在させず、実装と環境変数例を一致させてください。
サービスロールキーは RLS を迂回できるため、通常のユーザー操作には使わず、必要な場合もサーバーで認可を行います。

SNS のクライアント ID / シークレット等は、実際に選んだ認証方式で必要なものだけを追加します。Supabase 側で管理する OAuth シークレットは、その設定先で保持し、不要にアプリへ複製しません。

- ローカルの値は .env.local、配信環境の値はホスティング側の設定で管理する。
- .env* の実値を .gitignore で除外し、.env.example だけを例外として管理する。
- .env.example は変数名・空欄・説明のみ。秘密値、個人情報、実ユーザーのトークンは入れない。
- NEXT_PUBLIC_ を付けた値はブラウザーに公開される。秘密キーには付けない。
- 開発・プレビュー・本番は資格情報を分ける。必須変数が不足したら変数名だけを案内する。
- 漏洩したキーは削除だけで済ませず、失効・再発行する。

## 開発フロー

**Codex で実装 → localhost で確認 → チェック → GitHub に commit / push → Vercel で配信**を基本とします。
Vercel の自動配信は Git 連携・対象ブランチ・環境変数の設定後に有効になる想定です。この文書の追加だけで、アプリが配信された状態にはなりません。

通常の機能変更はブランチと PR にまとめ、既存コードと依存関係を確認してから実装します。
認可、満員時、同時入室、期限切れ、マイク拒否、再接続を検証し、ブラウザーで Value → Signup → 招待復帰 → 入室 → 音声 → 退出を確認します。
実装が進んだら、この README の実行方法・変数名・実装状況も同時に更新してください。
